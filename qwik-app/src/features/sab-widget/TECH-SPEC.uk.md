# SAB Widget: технічна специфікація прототипу

## Призначення

SAB Widget - горизонтальний віджет зі спортивними айтемами. Прототип перевіряє, як список айтемів поводиться при різній кількості контенту, різній максимальній кількості рядків і різному типі пристрою.

Поточна реалізація побудована на Qwik, TypeScript і Tailwind CSS. Логіка розкладки винесена окремо від UI, щоб її можна було перенести в інший environment.

## Структура фічі

- `sab-widget.tsx` - головний компонент віджета.
- `ui/sab-widget-item.tsx` - UI одного айтема.
- `lib/sab-widget-layout.ts` - розрахунок кількості рядків і розподіл айтемів.
- `types/sab-widget-types.ts` - типи пропсів, айтемів і варіантів віджета.
- `data/sab-widget-items.json` - mock-дані.
- `views/sab-widget-tab-view.tsx` - demo view з різними сценаріями.
- `index.ts` - public export фічі.

## Дані

Кожний айтем має мінімальну структуру:

```ts
type SabWidgetItemData = {
    title: string;
    imageSrc: string;
};
```

У прототипі дані беруться з `data/sab-widget-items.json`. Для production очікується, що ці дані можуть приходити з API, CMS або іншого джерела, але структура айтема має залишатись сумісною.

## API компонента

```ts
type SabWidgetProps =
    | {
          view: "tabs";
          device?: "desktop" | "mobile";
          itemsQuantity?: number;
          maxRowsDesktop?: number;
          maxRowsMobile?: number;
      }
    | {
          view: "rounded" | "square";
          device?: "desktop" | "mobile";
          itemsQuantity?: number;
      };
```

Поточний прототип реалізує поведінку для `view: "tabs"`. Варіанти `rounded` і `square` зарезервовані в типах для подальшого розвитку.

Параметри:

- `view` - тип віджета.
- `device` - тип пристрою. Якщо не передано, використовується `desktop`.
- `itemsQuantity` - кількість айтемів для показу в demo/prototype режимі.
- `maxRowsDesktop` - максимальна кількість рядків для desktop, за замовчуванням `1`.
- `maxRowsMobile` - максимальна кількість рядків для mobile, за замовчуванням `1`.

## Визначення пристрою

У demo route пристрій визначається на сервері через `user-agent`:

- mobile: якщо user-agent містить `android`, `iphone`, `ipad`, `ipod` або `mobile`;
- desktop: fallback.

Це приблизне SSR-визначення. Для production його можна замінити на власну backend-логіку, edge middleware або явний параметр від платформи.

## Розрахунок ширини

Оскільки на сервері немає реального DOM layout, ширина айтема оцінюється приблизно:

```ts
estimatedWidth =
    itemHorizontalPadding +
    itemImageWidth +
    itemContentGap +
    title.length * averageTitleCharacterWidth;
```

Поточні константи:

- padding по горизонталі: `24px`;
- іконка: `24px`;
- gap між іконкою і текстом: `8px`;
- gap між айтемами: `8px`;
- середня ширина символа: `8px`;
- максимальна ширина контейнера desktop: `1440px`;
- максимальна ширина контейнера mobile: `425px`;
- мінімальне заповнення найкоротшого рядка: `80%`.

Це не pixel-perfect вимірювання, а серверна евристика для стабільного першого рендера.

## Визначення кількості рядків

Алгоритм:

1. Беремо потрібну кількість айтемів.
2. Оцінюємо ширину кожного айтема.
3. Рахуємо загальну приблизну ширину всіх айтемів.
4. Вибираємо базову ширину контейнера:
    - `1440px` для desktop;
    - `425px` для mobile.
5. Рахуємо кількість рядків:

```ts
rowsByFill = Math.floor(totalWidth / (containerWidth * 0.8));
rowsCount = clamp(rowsByFill, 1, maxRows);
```

Якщо айтемів немає або `maxRows <= 0`, кількість рядків дорівнює `0`.

## Розподіл айтемів по рядках

Айтеми не діляться механічно на рівні частини. Щоб зберегти порядок із JSON і водночас вирівняти рядки по довжині, використовується greedy-алгоритм:

1. Створюється потрібна кількість порожніх рядків.
2. Айтеми проходяться в оригінальному порядку.
3. Кожний наступний айтем додається в поточно найкоротший рядок.
4. Ширина цього рядка оновлюється.

Таким чином порядок обходу айтемів зберігається, але візуально рядки стають більш збалансованими.

## Скрол і взаємодія

Контейнер має горизонтальний overflow. Scrollbar прихований через CSS-клас `scrollbar-none`.

На mobile горизонтальний свайп працює нативно. На desktop додана підтримка drag-scroll мишкою через Pointer Events:

- `pointerdown` запам'ятовує стартову позицію;
- `pointermove` змінює `scrollLeft`;
- `pointerup`, `pointercancel`, `pointerleave` завершують drag.

Drag-scroll застосовується тільки для `pointerType === "mouse"`, щоб не конфліктувати з нативною mobile-поведінкою.

## Styling

UI побудований на Tailwind CSS. Кольори беруться з CSS custom properties:

- `--background-main`;
- `--text-title`;
- `--text-body`;
- `--text-subtitle`.

Це дозволяє підключати теми без переписування компонентів.

## Demo view

`SabWidgetTabView` генерує матрицю сценаріїв:

- `itemsQuantity`: `5`, `10`, `15`, `20`, `25`;
- `maxRows`: `1`, `2`, `3`;
- поточний device показується в описі.

Мета demo view - швидко оцінити поведінку віджета в браузері без читання коду.

## Обмеження прототипу

- Вимірювання ширини айтемів приблизне, бо виконується без DOM.
- `itemsQuantity` існує для тестування і не є обов'язковим production API.
- Для production бажано додати стабільний `id` для айтемів замість використання `title` як key.
- `rounded` і `square` поки описані типами, але їх UI-логіка ще не реалізована.
- SSR device detection через user-agent є евристикою, не абсолютною гарантією.

## Рекомендації для production

- Перенести layout-алгоритм як окремий pure module, незалежний від UI-фреймворку.
- Зберігати тему через design tokens і CSS variables.
- Додати unit-тести на:
    - clamp кількості айтемів;
    - розрахунок кількості рядків;
    - розподіл айтемів у найкоротший рядок;
    - edge cases з `0` айтемів.
- Додати production-модель айтема з `id`, `title`, `imageSrc` і, за потреби, metadata.
